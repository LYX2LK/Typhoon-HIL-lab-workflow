# 水泵控制器 HIL 需求与接入准备

本文供项目维护者、案例接入人员及参与开发的 Agent 使用，整理汉象技术方案中水泵控制器这一具体需求对象。项目同时维护其他教学案例与应用资源，整体选型见[案例导航](resources.md#案例层次与选择依据)。当前阶段为需求整理与材料准备；水泵模型、控制板接口和实际测试判据仍需补齐。

## 来源与当前状态

主要依据为[汉象技术方案](<../../docs/电机硬件在环（HIL）及自动化测试 - 技术方案.pdf>)，版本 V.20261021-1.0，编写人为刘礼豪，编写日期为 2026 年 10 月 21 日。据项目成员提供的群消息，该文件于 10 月 22 日发送，说明为“文档是根据之前沟通整理的内容，方便你们查阅”。

方案提供测试对象、系统架构、故障类型与自动化接口路线。各项能力在本文中按“方案提出”“项目已有证据”“待确认”分别记录；交付内容、负责人和验收要求需要结合实际任务明确。本文引用的 PDF 页码按文件页序计数，包含封面和目录。

同期 ChatGPT 分析《分析技术方案》作为问题梳理参考；技术需求以原始方案及后续确认材料为依据。原始方案与波形位于上级 docs，独立交付本项目时应按实际范围附上来源材料。

## 本专题的工作范围

本专题沿用[路线图](roadmap.md)中的三个方向：把测试要求转为案例接入需求，验证现有工作流对自动化测试的支撑，明确 Agent 与实验执行系统的职责。本文维护水泵的具体缺口和推进条件；项目下一实例的选择综合任务、材料、运行条件和能力增益确定。方案第四章的四个用户案例单独列入[应用资源](resources.md#供应商介绍的应用案例)。

工程目标是复用模型加载、实验执行、数据采集、记录和复核流程，将案例差异集中在模型接口、实验配置和分析方法中。接到具体材料后，按[模型接入方法](model-integration.md)选择配置复用、适配器扩展或新增适配器。当前先维护本需求记录；模型、配置及判据具备后，再按[案例接口](case-interface.md)登记可执行案例。

## 案例需求记录

| 项目 | 方案提出或当前已取得的信息 | 接入前需要补充的信息 |
|---|---|---|
| 被测对象 | 实物 48V 水泵控制器，重点验证嵌入式算法、控制器行为及异常处理能力，见 PDF 第 3、6 页 | 控制板型号与版本、MCU 与固件版本、控制方式、实验负责人 |
| 物理边界 | 方案以控制器引脚为界，保留 MCU、驱动和采样电路，外围电机、传感器和功率器件由实时仿真模拟，见第 3 页 | 实际接线图、各注入点及保留电路、引脚方向、量程、极性、接地与隔离方式 |
| 模型需求 | PMSM、逆变器；提出同时仿真两台电机的需求，见第 3 页 | 可运行模型、依赖文件、参数来源、负载特性、控制部分位于模型还是实物板；首个实验是否需要双电机 |
| 输入数据 | 方案提出实测异常波形复现；本地已有 tu1–tu4 CSV 与对应图片 | 信号来源、测量点、单位、探头倍率、时间轴、采集设置、标签及标签依据 |
| 正常工况 | 转速、转矩闭环控制验证，见第 4 页 | 初始条件、供电、负载、参考值、稳定时间、采集窗口和误差阈值 |
| 异常工况 | 供电毛刺，传感器异常，位置与通信异常，缺相/短路/MOS 驱动异常，偶发故障，外围参数漂移，见第 4、10–12 页 | 首个异常的测试目的、注入位置、幅度、持续时间、触发方式、恢复方式及预期响应 |
| 预期判定 | 稳态、动态、保护、波形质量、鲁棒性、故障识别等维度，见第 13–14 页 | 每个用例的观测信号、指标公式、判定窗口、阈值、参考来源与确定人 |
| 软硬件依赖 | HIL404、上位机软件与 Python API、实物控制器、可编程波形电源及电压转换板，见第 6、11–12 页 | 实际设备清单、软件与许可条件、扩展卡、仪器驱动、连接与操作责任 |

方案列出的工况用于梳理覆盖范围，首轮按实际材料选择正常基准和一个异常。每个故障分别说明是在模型中改变状态、在信号接口施加异常，还是通过外部电源施加真实电气激励。

## 需求与现有能力的对应

已有能力及原始证据统一参见[验证状态](validation.md)。以下对应关系用于选择复用部分，水泵案例的实际结果随接入实验形成。

| 自动化环节 | 项目已有基础 | 水泵案例需验证的内容 |
|---|---|---|
| 模型加载与初始化 | 现有模型的准备、编译、Virtual HIL 加载和参数读回流程 | 供应商模型来源、依赖、编译目标、控制结构和初始化顺序 |
| 信号发现与映射 | 适配器能力描述、信号查询、采集列与单位映射 | 控制器参考、反馈、故障状态及保护信号的名称、方向、单位与可观测性 |
| 实验执行与事件 | 案例批次运行；Boost 与感应电机阶跃有固定事件及实际生效证据 | 每种故障的实施机制、设置阶段、事件时刻及生效观测信号 |
| 波形捕获 | 已有按实验配置采集并保存原始 CSV 的流程 | 触发、采样率、窗口、同步方式能否覆盖目标异常和控制响应 |
| 结果判定 | 确定性指标计算、预设判据、记录一致性与实验状态分开 | 适用于水泵控制器的参考与阈值；故障检出、保护动作和恢复的判定 |
| 统一结果输出 | 已有报告、JSON 返回、配置与代码快照、哈希核对及指标复算 | 新信号、事件、指标及外部数据来源能否进入可复核记录 |
| 外部波形与实体接口 | 路线图已明确数据输入及执行后端的扩展方向 | 波形导入与保真度、HIL404 外部 I/O、实物控制器及电源协同的专项验证 |

已有软件证据可用于确认公共流程。新增模型、信号和注入机制应针对变化部分验证；涉及真实电压注入或硬件接口时，需进入对应实体设备实验。Virtual HIL 的模型内结果与引脚处的实际信号分别留证。

## 优先确认的问题

| 问题 | 建议提供材料的一方 | 需要取得的具体结果 |
|---|---|---|
| 控制板与仿真器在哪里连接 | 控制板提供方、汉象 | 标注保留电路与替代部分的接线图和 IO/Pin 表，确定实际注入与测量位置 |
| 48V 主电源与 12V 辅助供电分别测什么 | 控制板提供方、汉象 | 每条供电链路的量程、负载、异常注入点及外置电源能力 |
| 哪些参数可以运行中修改 | 汉象、模型提供方 | 按具体元件/变量列出在线写入、模型内预设事件或编译前修改方式，并给出示例 |
| 波形复现需要什么精度 | 数据提供方、测试负责人、汉象 | 目标异常的时间与幅值特征、允许误差、测量方法；分别说明模型步长、采集、I/O 和外置电源时序 |
| SPI/I²C 异常能覆盖哪些情况 | 控制板提供方、汉象 | 实际协议、速率、帧格式、异常类型及演示条件；方案第 4 页的有限支持与后续故障描述需对应到同一工况 |
| 模型和自动化材料如何交付 | 汉象、模型提供方 | PMSM/逆变器模型、参数与依赖说明、最小加载/注入/采集脚本、参考数据及使用范围 |
| 首个案例怎样判定通过 | 测试负责人，相关提供方共同确认 | 正常基准、一个异常、预期响应、指标和阈值来源，以及结果确认责任 |
| 与大模型模块怎样连接 | 项目维护者、分析模块负责人；涉及供应商接口时由汉象配合 | 任务输入、工具调用、结果返回及分析输出约定，明确各方交付范围 |

以上为建议协作分工，具体责任人随任务确认。方案中的 ISO 7637 等表述先作为需求线索；若任务要求标准符合性，应补齐适用版本、具体条款、脉冲条件及测试方法。

## 四组波形的接收准备

原始文件位于[波形目录](../../docs/tu/tu/)：tu1–tu4 各有 CSV 和 PNG。当前只确认文件存在，尚未在本需求记录下完成数值复核或回放验证。

接收时保留原始文件，登记来源、文件哈希、通道含义、单位、时间轴与采集条件。正常/异常标签、标签提供者及依据分别记录。数值检查应确定异常幅度、持续时间和关键边沿，再判断采用离线分析、模型内回放还是外部仪器激励。

若需要重采样、插值、时间平移或幅值缩放，应保留转换方法与派生文件，并在实验前确定比较窗口和误差指标。采样间隔、异常持续时间与设备可复现的时间尺度分别核对。完成依据是明确数据能支撑的测试问题和实施路径。

## 本专题下一步工作与完成依据

| 顺序 | 工作 | 启动条件与交付 | 当前状态 |
|---|---|---|---|
| 1 | 完善需求与缺口记录 | 按本文逐项补充来源、确认结果及责任人；明确可复用部分和候选接入路径 | 已形成需求记录，关键材料待补 |
| 2 | 收集最小模型和接口材料 | 优先取得接线/IO 表、模型与参数、依赖说明、最小脚本和参考判据 | 待材料与分工确认 |
| 3，可与 2 并行 | 整理四组波形 | 补齐采集元信息并完成数值检查，给出离线分析或回放用途及精度要求 | 待元信息确认与数据检查 |
| 4 | 定义正常基准和一个异常 | 根据模型、接口、测试价值及可观测性选定；固定事件、信号、窗口、指标与阈值 | 待 2、3 的相关条件具备 |
| 5 | 完成最小自动化实验 | 模型支持软件闭环时先验证 Virtual HIL；依赖实物响应时按设备条件验证；交付原始数据、生效证据、报告与复核结果 | 待实验条件与判据明确 |
| 6 | 固化可复用能力 | 按实际差异扩展适配器、数据入口或执行支持，登记案例并更新能力、操作及验证文档 | 由最小实验结果确定范围 |

每次实验返回实际结果目录，分别报告 record_status 与 experiment_status。新增能力融入对应接口与教程；实际结果进入验证状态和验证索引，本文持续维护需求、缺口及下一步安排。

## Agent 与执行系统的职责

Agent 负责理解测试目的、整理缺口、编排用例、提出参数与判据候选、调用 Python 工具及辅助分析。实验前固定采用的配置与判据；实际施加、采集、计算和复核由已明确的执行流程完成。

实时仿真闭环、时序敏感控制和底层安全保护由确定性的仿真器、控制器及测试执行系统承担。Agent 的调用请求、实际执行配置和返回结果应能关联；分析结论应指向原始数据与计算依据。大模型分析形成独立结果，关联输入和方法版本。

日常任务表达与结果核对见 [Agent 工作流](agent-workflow.md)；长期接口与部署安排见[路线图](roadmap.md)。
