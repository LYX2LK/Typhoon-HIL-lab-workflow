# 故障排查与保留证据

本文帮助组员根据失败阶段定位问题。先记录执行命令、实际结果目录和日志中的第一处错误，再处理原因。修改后重新运行并保留新目录，便于比较修复前后的行为。

## 先判断是哪一层失败

| 现象或阶段 | 优先检查 | 下一步 |
|---|---|---|
| `lab.ps1` 找不到 | 是否在项目根目录，是否复制了完整项目 | 从包含入口的目录执行命令 |
| PowerShell 无法执行脚本 | 错误是否来自脚本执行策略或组织策略 | 保留完整报错，按本机已有策略处理；可请 Agent 使用等效的受允许入口 |
| Python 找不到 | `environment.local.json` 的 `typhoon_home` 及配套 Python 路径 | 修正本机配置，重跑 `doctor` |
| `typhoon` 等模块导入失败 | 使用的是否为 Typhoon 配套解释器，安装是否完整 | 比对 `doctor` 输出中的实际解释器路径 |
| `doctor` 通过，编译失败 | 模型、元件库、属性名、参数值和许可 | 阅读编译日志，核对官方示例及本版模型 |
| 编译通过，加载失败 | 是否使用本次编译产物，Virtual HIL 许可和目标配置是否可用 | 核对加载日志和模型设置 |
| 启动或采集异常 | 是否加载成功、信号名是否存在、采集设置是否有效 | 对照 `inspect` 与采集日志 |
| 波形时间或幅值不合理 | 单位、源 RMS、频率、采集起点及有效采样设置 | 查实际配置与原始 CSV |
| 判定 `failed` | 具体判据、稳态窗口、模型参数及参考值拓扑 | 重算指标，解释偏差后再决定修订实验 |
| 报告缺图或缺指标 | 原始文件是否齐全，报告生成阶段是否报错 | 运行 `verify`，按日志定位缺失文件 |

表内原因是排查顺序，是否适用于本机应结合实际日志判断。新增已解决问题时，在文档中记录报错、原因、处理命令和复验目录。

## 采集设置可能被调整

TyphoonTest 官方 [`start_capture`](<../../Typhoon HIL Control Center 2026.3/Documentation/typhoontest_html/api/typhoon.test.capture.start_capture.html>) 说明：采样率和时长受系统约束，接口可能使用最接近的可用值并给出警告。遇到警告时，查看返回的有效值和原始时间列；报告应说明实际采集设置。

Virtual HIL 按仿真时间运行，电脑执行时长与采集的仿真时长可能不同。检查时间窗口应看数据中的仿真时间。

## 避免相互干扰

同一次自动实验期间保持一个运行入口。若正在 HIL SCADA 中手动操作同一仿真，应先完成并停止该操作，再运行自动实验。异常退出后查看当前仿真状态和日志，由项目执行流程停止本次仿真，再重新运行。保留用户应用窗口供核对。

## 如何向 Agent 描述问题

> 我执行了 `<完整命令>`，结果目录是 `<实际目录>`，失败阶段为 `<编译/加载/采集/分析>`。请读取日志中的首次错误，检查配置和对应官方 API，修复后用同一配置重跑，保留两次目录并比较。

要获得有效诊断，请提供或让 Agent 读取：本机环境检查、运行配置、模型版本摘要、日志和原始数据。实验失败后仍可整理已经取得的数据，但报告中需保留失败状态及缺失项。
